# Relationships, Lifecycle, Ownership, and RLS Considerations

## Relationships

### One-to-many
- One profile can own many cases.
- One case can contain many documents.
- One case can contain many evidence items.
- One case can contain many timeline events.
- One case can contain many witnesses, victims, and accused persons.
- One case can generate many charge sheets.
- One case can have many chat messages.
- One case can have many audit logs.

### One-to-one or zero-to-one
- One document may have zero or one OCR result.
- One profile may be associated with zero or many generated charge sheets.

## Expected Row Lifecycle

### profiles
- Created when a user signs up or is provisioned.
- Updated when role or display information changes.
- Rarely deleted; prefer soft archival or disablement if needed.

### cases
- Created when a new investigation begins.
- Status transitions from draft to active to closed or archived.
- Deleted only under explicit retention policy and with audit trace.

### documents
- Created on upload.
- Processed asynchronously after upload.
- May remain immutable after processing to preserve audit integrity.

### ocr_results
- Created after document processing.
- Updated only if reprocessing occurs; otherwise preserve prior versions.

### evidence_items
- Created once evidence is logged.
- Updated as chain-of-custody or status changes.

### timeline_events
- Created as events are discovered or recorded.
- Generally append-only.

### chat_messages
- Created as users interact with the assistant.
- Retention should follow compliance policy.

### audit_logs
- Append-only.
- Never updated or deleted in normal operation.

## Data Ownership

### Ownership model
- cases are owned by the creating user profile, with possible future multi-assignee support.
- documents are owned by the case and uploaded by a user profile.
- OCR results are owned by the document and case.
- evidence, witnesses, victims, accused persons, and timeline events are owned by the case.
- chat messages are owned by the case and the user who authored them.
- audit logs are owned by the system and the acting user profile.

### Recommended ownership rules
- Business records should be scoped to a case.
- User-created content should be attributed to the responsible profile.
- System-generated records should be clearly marked as generated by the platform.

## Future RLS Considerations

### Recommended RLS direction
- Use Supabase Row Level Security once the application access model is finalized.
- Enforce access based on case membership, ownership, and role.

### Suggested policy foundation
- Users can read and update cases they own or are assigned to.
- Users can read documents and evidence belonging to accessible cases.
- Audit logs should be readable by authorized roles only and should remain append-only.
- System-generated records should not be directly editable by end users.

### Additional considerations
- Introduce a case_members table later if multi-user access is required.
- Introduce role-based policies for investigators, analysts, auditors, and admins.
- Keep public access out of scope unless explicitly required.
